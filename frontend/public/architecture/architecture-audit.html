01System Overview

Type: a metadata-driven, rule-configurable payroll calculation engine for the Nigerian statutory regime. It is not a generic workflow tool with payroll bolted on, and not a hardcoded per-country calculator — the calculation graph itself (which components run, in what order, feeding what totals) is data, not code.

Architectural style: layered and domain-driven, matching the layering documented in the project's own CLAUDE.md and confirmed in the source tree:

LayerLocationRule observed
API routesbackend/api/routes/Thin — orchestration and validation only
Application servicesbackend/application/Owns transactions, lifecycle transitions, retry orchestration
Domain logicbackend/domain/payroll/, backend/domain/rules/Pure functions — no DB imports, confirmed in paye.py, pension.py, nhf.py
Repositoriesbackend/infra/repositories/Raw SQL, workspace-scoped in SQL for most tables

Design philosophy, as evidenced by the code itself:

  • Configuration over branching. sequential_executor.py dispatches through a handler registry (register_handler()) keyed by calculation_method, not an if/elif ladder — new statutory contributions (NSITF, ITF) were added by registering a handler, not editing the core loop.
  • Fail loud, not silent. Missing pension rates raise; unrecognised rule methods produce an explicit not_applied trace entry rather than being dropped; a missing historical rule version raises NoHistoricalRuleVersionError rather than falling back to the current rate. This pattern — reject rather than guess — recurs across the codebase and is the strongest evidence of a deliberate correctness-first design stance.
  • Temporal correctness as a first-class concern. The RULE-VER-1 rule-versioning system and statutory_rule.effective_from exist specifically so a correction run for a past period recalculates under the rules that applied then, not today's rules.

02Core Capabilities — Code-Verified

Sequential calculation engineFull

Payroll components execute in priority order (BASIC → HOUSING → TRANSPORT → rule-injected pay → GROSS_PAY → PENSION → TAXABLE_INCOME → PAYE → NHF → HEALTH → DEVELOPMENT_LEVY → employer costs → NET_PAY), each handler reading only the accumulated context so far — a genuine pipeline, not a flat spreadsheet of independent formulas.

Rule execution modelFull

Workspace-defined payroll_rule records support five calculation methods: unit_multiplier, daily_rate_deduction (with per-component proration strategy and multi-period-spanning group handling), fixed_amount, ot_multiplier (rate-code driven overtime, shift-gated), and percentage_of_sum. Rules run before the sequential executor and inject components at priority 50.

Rule versioning & historical resolutionFull

Rule sets are snapshotted per (workspace, effective_from) and auto-published; once a payroll_run references a rule set it is locked from further edits. Correction runs resolve rates against the rule set that was active on the original reference_date, and raise rather than silently substitute the current rate when no historical version exists.

Auditability & traceabilityFull

Every executed component writes a trace entry (method, class, result, and — for period-sensitive calculations — the annualization factor used) into component_trace_jsonb, seeded with a period-context header. Rule-evaluator trace entries (resolution source, rate used, warnings) are merged in wholesale — a prior gap where only one rule type's trace survived has been fixed. Lifecycle transitions write to audit_log with old/new value diffs.

Legacy calculation pathPartial

When a caller doesn't supply component_metadata, the engine falls back to a legacy pipeline that produces a payroll result with no audit trace (component_trace_jsonb is explicitly set to None). This path is still live and instrumented — its usage is tracked and exposed via an ops endpoint — rather than removed.

Input handlingFull

Payroll inputs carry a category (EARNING, DEDUCTION, STANDARD, PAYE_ONLY) enforced by a DB constraint; PAYE_ONLY rows raise taxable income without touching gross or net pay. Inputs are inserted unclaimed and claimed onto a run by reference date; future-dated inputs are never auto-claimed. Bulk upload of pay inputs and bulk enrollment onto payroll are separate code paths writing to separate tables, deliberately decoupled since Sprint 22.

Payroll lifecyclePartial

Runs progress DRAFT → CALCULATING → CALCULATED/PARTIAL → APPROVED → LOCKED → PAID, enforced by a DB trigger on rank rather than an explicit edge list. LOCKED/PAID runs are immutable to edits. Retry is PER_EMPLOYEE only — FULL_RUN retry was deliberately retired and now raises on invocation. Gap: the DB trigger recognises a VALIDATED status that does not exist in the Python status enum — a single-source-of-truth drift, not observed to cause a functional failure but worth reconciling.

Statutory calculationsFull

PAYE uses the cumulative annualized method (period income × annualization factor, banded, de-annualized) — correct for non-monthly periods, not just a monthly shortcut. Bands were corrected to NTA 2025 thresholds in a scoped, non-destructive migration. Pension, NHF, Health Insurance, Development Levy, NSITF, and ITF are all implemented as pure Decimal functions in backend/domain/rules/; pensionable base and ITF eligibility (≥5 employees, ≥₦50M YTD payroll) are both config-resolved, not hardcoded.

03Differentiators — Based on Implementation

What actually separates this from a typical bespoke payroll build, evidenced in the code rather than claimed in a pitch deck:

  • The calculation graph is data, not code. Execution order, component classification (taxable/non-taxable/employer-cost), and rate values live in component_metadata, client_component_metadata, and rule_set_item.rule_definition_json. Reclassifying a component or changing a rate is a database write, evidenced by the override path at sequential_executor.py:667–679 — no equivalent exists in a hardcoded formula system.
  • Rules are versioned like code, not overwritten like config. rule_set snapshots are immutable once referenced by a run (rule_set_service.py raises RuleSetLockedError rather than allowing a retroactive edit) — most SME payroll spreadsheets and even many commercial tools cannot reproduce a payslip from six months ago under the rules that applied then. This one can, for rule-defined components — see the rate-code exception below.
  • Every computed number carries its own provenance. component_trace_jsonb records not just the result but the method, resolution source, and (for time-sensitive figures) the exact annualization factor used — built for reconstructing "why is this payslip this number" without re-running the engine.
  • JSONB is used for genuine schema flexibility, not as a dumping ground. salary_definition.components_jsonb, metadata_json, and overrides_json all have a defined, code-enforced shape per calculation_method, read through typed accessors — not free-form blobs read ad hoc.

04Limitations & Gaps

  • Not implementedRate code versioning. rate_code_registry has no effective_from column. Overtime/shift-rate changes cannot be reproduced historically the way rule and statutory changes can — the one place the "temporal correctness" design goal isn't yet met. Flagged as a TODO in the code itself (rule_evaluator.py:477).
  • Not implementedDirect-pay input source (period_input_components). The executor's function signature accepts this parameter "for API stability" but never uses it — a stated future extension point, not a bug.
  • PartialLegacy executor fallback. Still reachable, produces payroll results with zero audit trace. Anything calling it without component_metadata silently loses traceability, even though the run itself succeeds.
  • PartialStatus model. Two sources of truth (Python enum vs. DB trigger) disagree on whether VALIDATED is a real status. No observed functional break, but it means a developer reading only the Python code has an incomplete picture of what the database will actually accept.
  • Implemented, not exposed via UIRule-set / rule-versioning history. The backend has a full snapshot-and-lock system for rule sets; no frontend page lets an operator browse published rule sets or their effective dates. An operator today cannot see "what rules were active for the March run" without querying the database directly.
  • Implemented, not exposed via UIExecution trace / legacy-executor-stats. Both exist as backend endpoints with no corresponding page — an operator cannot currently see, from the UI, whether a given run used the audited or the un-audited calculation path.

What would block this from being production-ready at enterprise scale: not the calculation logic itself, which is unusually rigorous for its stage — it's operational surface area. Multi-country statutory support doesn't exist beyond Nigeria (no evidence of a second country_code ruleset in the domain layer). The rate-code versioning gap means overtime corrections on past periods are not fully auditable. And the workspace-scoping inconsistency in two repositories, while not currently exploitable, means tenancy isolation depends partly on caller discipline rather than being structurally guaranteed everywhere — the kind of thing that becomes a real risk as more routes get added by more people.

The honest read: this system is structurally more agile than an enterprise suite for a single-country, single-bureau context — the metadata-driven design genuinely delivers that. It has not been tested against the volume, multi-country breadth, or hostile-input hardening that the enterprise incumbents have absorbed over decades. It is not a replacement for SAP/Oracle/ADP at enterprise scale today; it is a credible, auditable alternative for the SME/bureau segment those vendors under-serve on cost and flexibility.

06Value Proposition — Derived from Real Capabilities

Technical fact

Component classification, rates, and execution order live in DB metadata, not code (§2, §3)

Business value

A new earning/deduction type, or a client-specific rule, can go live same-day — not after a development sprint

Technical fact

Rule sets are versioned and locked once used by a run; correction runs resolve historical rates (§2)

Business value

A payslip from any prior period can be defended and reproduced under an audit — the answer to "why was this employee paid this" doesn't depend on anyone's memory

Technical fact

component_trace_jsonb records the method and resolution source behind every figure (§2)

Business value

Statutory or client queries can be answered by pulling one record, not by re-deriving the calculation by hand

Technical fact

Fail-loud design: missing rates and unresolvable historical rules raise errors rather than substituting a guess (§1)

Business value

Silent miscalculation — the failure mode that actually damages a payroll bureau's reputation — is designed against, not just tested against

0730-Second Sales Summary

Most payroll systems are either rigid — every rule change needs a developer — or opaque — you can't see how a number was actually calculated. This one is built differently: the rules that decide how someone gets paid live in configuration, not code, so a client-specific pay rule can go live in a day instead of a sprint. And every single figure on every payslip carries a record of exactly how it was worked out, so if a client — or a tax authority — asks "why is this number what it is," there's a real answer, not a shrug. It's built for a payroll bureau that needs to move fast for clients without losing the paper trail.
