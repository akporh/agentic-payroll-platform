# Stage 01 Output: Current Operating Model — Summary

This is a synthesized, descriptive narrative of how the payroll platform currently operates, built entirely from the 46 confirmed findings in `../findings.md`. It is descriptive only — no recommendation, no agent design, no redesign. Every claim below traces to a numbered finding; read `findings.md` for the underlying code/migration citations.

## 1. Tenancy and onboarding

A `workspace` is the tenant unit. It is created via `POST /workspace` with just `name`/`country_code`/`base_currency`; a modeled parent `account` entity exists in the schema but is never populated by this route (F-01-01). Every workspace starts `DRAFT` and must pass through a strict, forward-only six-state onboarding machine — `DRAFT → STRUCTURE_DEFINED → COMPENSATION_DEFINED → RULES_DEFINED → READY → LIVE` — gated by structural prerequisite checks at each step (pay_cycle/grade/designation, then salary_definition, then an active payroll_rule, then platform-level component_metadata for the country) (F-01-04). No payroll_run can be created until the workspace is `LIVE`, enforced by a DB trigger (F-01-02). Structural configuration (pay cycles, grades, designations, salary definitions, rules, component metadata) can be created either through a bulk onboarding-commit flow or through individual per-entity routes — both are live, parallel entry points (F-01-05).

Workspace scoping is applied as a column/FK on nearly every domain table. Two tables are confirmed exceptions: `employee_contract` (scoped by joining through `employee.workspace_id`, consistently applied everywhere checked) and `payroll_reconciliation` (which has no workspace scoping mechanism at all — see §6) (F-01-03, F-01-15, F-01-33).

## 2. Compensation structure: components, grades, designations, salary definitions

Salary components are modeled at two tiers: a platform-level `component_metadata` table (keyed by component/country/version) and a per-workspace `client_component_metadata` override table. Legal/tax attributes (`is_pensionable`, `is_taxable`, `is_proratable`) live inside a JSONB `legal_role` blob rather than as dedicated columns, and a second, differently-named boolean column (`active`, alongside the older `is_active`) was added specifically to gate participation in the calculation pipeline (F-01-06). At least one component (`PH_OT`) was seeded without its pensionable flag pending a handler fix, per the seeding migration's own comment — whether that gap has since been closed was not re-verified in this stage (F-01-07).

Grades and designations are workspace-scoped lookup entities. Critically, `salary_definition` — the record that actually holds component amounts (`components_jsonb`) — has no `grade_id`/`designation_id` column; that binding lives instead on the employee's `employee_contract` row. `salary_definition.code` follows a `DESIGNATION_GRADE` naming convention, but nothing in the schema enforces that convention (F-01-08). Separately, a `grade.total_monthly` + percentage-split mechanism exists as an alternative way to derive BASIC/HOUSING/TRANSPORT/UTILITY, coexisting with the `salary_definition.components_jsonb` path — which one applies for a given employee, and how the engine chooses, was not traced to source in this stage (F-01-09).

Pay cycles and payroll rules follow a strict single-active/date-resolved pattern: exactly one active pay cycle per workspace (enforced at both application and DB level), and rule resolution is always date-driven (`effective_from <= as_of_date`, latest first) — `is_active` is never used alone to pick a rule (F-01-10). Published rule sets (`rule_set`/`rule_set_item`) are immutable snapshots; once a rule set has been used by a run, it cannot be silently overwritten (F-01-11). Workspace payroll-behaviour config (PH mode, weekend-PH precedence, leave/PH overlap rules) is validated by a Python allowlist that a code comment says "must match" a separate DB CHECK constraint — two independent places encoding the same set of legal values (F-01-12).

## 3. Employee lifecycle: registration, enrollment, contracts

Employee "Upload" (HR registration) and "Enroll" (payroll assignment) are deliberately separate operations. Upload can create an employee with no salary definition at all (an "unenrolled" state); Enroll later assigns `salary_definition_code` and rejects employees who are already enrolled (F-01-13). Payroll-run employee selection is an inner-join query filtered on `status = 'ACTIVE'` — employees who are `INACTIVE` or still unenrolled are silently excluded from a run with no per-employee error, only a workspace-level "no active employees" error if the whole set is empty. `employee.status` itself has no DB CHECK constraint; its two legal values are enforced only in Python (F-01-14).

`employee_contract` has no `workspace_id` of its own — every scoped operation joins through `employee`. Overlap between contracts for the same employee is prevented by a DB-level GiST exclusion constraint, and at most one open (`end_date IS NULL`) contract per employee is enforced by a partial unique index (F-01-15). The `shift_type` field is nullable and is treated inconsistently across two paths: the payroll-run OT-derivation path defaults a NULL to `'DAY'`, while the timesheet upload/derivation pipeline hard-rejects any entry with a NULL shift_type and asks the operator to fix the employee record (F-01-16).

## 4. Timesheets and payroll inputs

One-off payroll inputs (`payroll_input`) are DB-constrained to four categories (`EARNING`/`DEDUCTION`/`STANDARD`/`PAYE_ONLY`) and non-negative quantities, with pre-migration checks that would have aborted the constraint's rollout had violating data existed. Bulk upload validates the same rules again in Python and treats an already-existing unclaimed duplicate as a per-row "skipped" outcome rather than failing the whole batch (F-01-17). The timesheet pipeline (upload → derive → approve) requires every entry for a period to reach `DERIVED` before approval is allowed, and approval atomically replaces prior unclaimed timesheet-sourced inputs for that employee/period (F-01-18).

Before a run executes, a Python-level readiness check (`payroll_readiness_service`) verifies every eligible employee has a salary definition, and — separately — a DB trigger verifies workspace-level preconditions (LIVE status, at least one statutory rule, tax bands, active component metadata for the country). The DB trigger does **not** check per-employee salary-definition presence; only the Python check does. If that Python check is ever bypassed, the run-execution query itself would simply exclude the unenrolled employee silently (inner join), rather than erroring the way the pre-check does — whether the pre-check is unconditionally invoked before every execution path was not confirmed in this stage (F-01-19, F-01-20).

## 5. Run creation and calculation

`payroll_run.run_type` (`REGULAR`/`ADJUSTMENT`/`CORRECTION`) has no DB constraint — it's an API-layer allowlist only (F-01-21). `payroll_run.status` transitions (`DRAFT → CALCULATING → {CALCULATED|PARTIAL} → APPROVED → LOCKED → PAID`) are enforced by a rank-based DB trigger that rejects backward or unknown moves; an earlier trigger generation had silently stopped enforcing anything after the application's status vocabulary changed underneath it, a gap that has since been fixed (F-01-22). Run creation itself is asynchronous: the HTTP response returns immediately after a DRAFT row is inserted, with the actual calculation deferred to a background task (F-01-23).

Calculation dispatches to one of two engines based purely on whether `component_metadata` is supplied: the production **sequential executor**, which evaluates ordered components by a DB-data-driven `execution_priority` and produces a full `component_trace_jsonb`; or a **legacy executor**, reachable only when `component_metadata` is absent, which is confirmed to skip workspace payroll rule evaluation entirely (not just tracing) and explicitly null out the trace field. Both real production call sites always supply `component_metadata`, so the legacy path is not observed to fire — but it remains live code, tracked by a dedicated monitoring endpoint (F-01-24, F-01-28). Rule-injected components receive a fixed synthetic priority (50) ahead of the gross-pay aggregation step (100); specific components like PAYE-only additions (95) and check-off dues (450) were seeded at deliberately chosen priorities relative to their neighbors (F-01-25).

Three snapshot tables plus a snapshot column capture the run's starting state (employee contract, component metadata, client overrides, salary inputs) in one atomic, idempotent write immediately after the DRAFT run is created; a failure here leaves the run permanently un-retryable (F-01-26). `salary_definition` itself is locked from editing only once a run using it has reached `PAID` — no DB-level lock exists for the entire DRAFT-through-LOCKED window, though a separate application-layer check (on the `patch_salary_definition` route specifically) does block edits while a run is `CALCULATED`/`PARTIAL`/`APPROVED`, via a query deliberately built to avoid a documented false-negative for in-flight runs. That same query's status allowlist includes two values (`SUBMITTED`, `PROCESSING`) that no code in the current application ever writes — meaning those branches are presently dead against current write paths (F-01-27, F-01-37, F-01-38).

## 6. Retry, reconciliation, and locking

Retry is a column on `payroll_run` (`retry_strategy`), not a separate request table — it has been relocated across schema versions and is now DB-constrained to a single legal value, `PER_EMPLOYEE`; `FULL_RUN` was retired at the database level, not merely disabled in application code, though the frontend still presents it as a selectable option that the backend will reject (F-01-30, F-01-31). Retry only reprocesses `payroll_result` rows marked `FAILED`, using a delete-then-insert pattern (never UPDATE) because a snapshot-immutability trigger blocks in-place changes; a run cannot be retried once `APPROVED`, `LOCKED`, or `PAID` (F-01-32).

`payroll_reconciliation` compares actual vs. expected run totals and is gated to `LOCKED` runs only (application-enforced, not DB-enforced). Its `MATCHED`/`MISMATCH`/`RESOLVED` statuses carry DB-level CHECK constraints guaranteeing `MATCHED` always means totals-equal — `RESOLVED` was deliberately introduced as a separate status specifically to avoid overloading `MATCHED`'s meaning when an operator manually closes out a mismatch (F-01-34, F-01-36). This table, however, has no `workspace_id` column at all, and every repository function and route scopes solely by `payroll_run_id` — a confirmed gap against the project's own "workspace scoping mandatory on every query" rule (F-01-33). A resolution-update function's docstring also disagrees with its own SQL (says "sets MATCHED," actually sets "RESOLVED") — a documentation/code mismatch with no observed functional impact (F-01-35).

`payroll_result` rows become immutable at the DB trigger level starting at `CALCULATED` — one step earlier than `APPROVED` — and `PAID` runs are immutable at the run level entirely (F-01-37, F-01-39).

## 7. Audit trail

Two structures exist for recording history: `audit_log` (before/after values, who, when) and `event_store` (event-sourcing-style). In practice, both are written to only for `payroll_run` status transitions — creation, approve, lock, mark-paid, and post-retry recompute. Reconciliation resolutions and configuration edits (salary definitions, pay cycles, contracts) have no entry in either table; their only trail is each record's own `created_at`/`resolved_at` timestamp, which does not capture who made the change or what the prior value was (F-01-40).

## 8. Operator-facing flows

The UI follows a coherent lifecycle: bureau dashboard (workspace list/creation) → workspace onboarding wizard → employee management (upload/enroll/edit/change-grade) → run creation/list → run results (tabbed: Results, Reconciliation, Timeline, Audit Log). Several configuration pages (rate codes, attendance codes, public holidays) sit alongside this lifecycle as independent top-level pages rather than embedded steps; rate-code management specifically is reachable from two separate places (F-01-41). A legacy `Reconciliation.tsx` page is a pure redirect, intentionally superseded by a tab inside the run-results page (F-01-42).

The designed path for correcting anything beyond a per-employee retry is to open a new payroll run (of type `ADJUSTMENT` or `CORRECTION`) rather than edit the existing one — stated directly in the product's own "cannot retry this run" messaging. However, `CORRECTION` is accepted by the backend but has no corresponding option in the run-creation UI, which only offers `REGULAR`/`ADJUSTMENT` (F-01-43). The results view also surfaces a specific, purpose-built warning icon when a component's rate had to fall back to the current (rather than historically correct) value during resolution — a targeted audit signal for silent rate substitution, though the exact producing code path was not traced in this stage (F-01-44).

## 9. Statutory-rule maintenance

New or changed statutory rates (PAYE bands, pension, NHF, health insurance, development levy) are added exclusively through Alembic migrations running raw SQL — there is no admin route or UI for this, confirmed by the complete absence of any such endpoint or frontend reference. PAYE tax bands are fully normalized into their own table with a DB constraint explicitly forbidding them from being duplicated inside the JSONB rules blob. The other statutory rates (pension, NHF, health insurance, development levy) remain as unstructured JSONB keys, read at runtime with silent Python-side default values if a key is missing — no equivalent normalization or anti-missing-key constraint exists for them (F-01-45, F-01-46).

## What this stage did not establish

Several threads were explicitly left open rather than guessed at, and are flagged in `findings.md` for later stages to resolve: whether the `PH_OT` pensionable-flag gap (F-01-07) has since been fixed; which code path selects between the grade-percentage and salary-definition-JSON component derivation (F-01-09); whether the payroll-run readiness pre-check is unconditionally invoked before every execution path (F-01-20); whether the `component_trace_jsonb` fallback-precedence branch in the single-row save path is ever actually exercised (F-01-29); and the exact code path that produces the `current_fallback` resolution-source audit flag (F-01-44).
