# Stage 08 → Stage 09 Handoff (Human Experience)

The mechanisms are designed; Stage 09 designs the surfaces. Per mechanism, the UI-relevant facts and constraints (surfaces, not screens — screen design is yours):

1. **Auth (C1)** [`auth-foundation-design.md`]: login (email/password, workspace selection from memberships); workspace **switcher** = new session (P6 — the UI must present switching as a context change, not a filter); session-expiry re-login (8h tokens, no refresh in v1); step-up modal (credential re-entry returning a `step_up_event_id`, 5-minute freshness — the UI should submit the approval promptly after step-up or expect a fresh prompt). Frontend's stored workspace selection becomes navigation state only.
2. **Audit rendering**: every audit/history surface must label pre-epoch rows `identity unverified (pre-auth era)` mechanically from `platform_metadata.auth_cutover_epoch`, and render actor display names via operator join (records store UUIDs). Statutory rows without `applied_change_id` render "migration-seeded (pre-C12)".
3. **Notification / work queue (C2)** [`event-audit-foundation-design.md` §4/§6]: `workspace_notification` (type, severity, read_at, entity linkage) and the **exception queue** over `exception_record` — the eight-stage lifecycle (open → assigned → resolved → verified → closed), one accountable owner, evidence display from `evidence_jsonb`, resolution codes (`CONFIRMED_ERROR_CORRECTED`, `CONFIRMED_CORRECT_DISMISSED`, `ESCALATED`). Prioritisation display is yours (severity + cutoff proximity from evidence fields). Stage 04's outcome definition (`exception-resolution-outcome.md`) is the binding workflow content.
4. **C10 confirmation UI** [`confirmation-protocol-design.md`]: renders **exclusively from `payload_jsonb`** (frozen at proposal — never from chat text); a distinct authenticated action, not a chat reply; must present terminal states (executed / rejected / expired / invalidated with "the underlying record changed since this was proposed" + both states); double-submit returns the recorded outcome — design for it.
5. **C12 approval UI** [`statutory-change-mechanism-design.md`]: proposal list + detail showing the full §3 evidence set (source citation with verbatim excerpt, deterministic diff, validation results, impact preview with before/after per component); approve requires the step-up modal; rejection requires reasoning text; `PLATFORM_ADMIN`-only surface, platform-level (not inside a workspace context); correction proposals additionally show the consumed-runs statement.
6. **C13/C14 flow**: mapping-proposal review (original header text alongside proposed mapping — Stage 03 matrix), then dry-run results view (`dry_run_execution.results_jsonb`: per-employee results + traces, amounts are strings), then commit gated on the successful dry run of exactly those rows (hash-checked — surface "re-run required" when rows changed after the dry run).
7. **C7 flags** arrive only as exception-queue records (§3) — no separate anomaly UI; evidence shows entered value, history median, ratio, threshold fired. Shadow-mode records are marked and excluded from operator-facing counts.
8. **DQ-005** (forwarded to you + Stage 11): whether `run_type = CORRECTION` is exposed in the UI or stays API-only — unchanged, still open, now with the C10/C12 surfaces giving it natural context.

Constraint carried: any frontend sprint in Phase 3 reads `docs/design/ui-decisions.md` first (standing project rule); nothing in this handoff overrides the platform's existing design-system decisions.
